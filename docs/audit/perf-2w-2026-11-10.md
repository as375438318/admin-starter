## 2. 结论与余量

1. **2 万行撑得住**：1GB 堆下堆增长仅 12 MB、0 次 Full GC；解析 74–180ms、目录装载 14–32ms、逐行校验 21–80ms，均不是瓶颈。
2. **瓶颈是持久化**：`DemoTaskRepositoryImpl.insertBatch` 是 `for` 循环逐行 `mapper.insert`，2 万行即 2 万次往返，耗时 6,726–7,964ms（占服务端总耗时 96%–98%），每次约 0.34–0.40 ms/行。`rewriteBatchedStatements=true` 已在 JDBC URL 上，但代码没有走批量语句，参数不生效。
3. **与早先“2–5 秒”的估算不符，如实修正**：实测 6.9–8.3s。差异全部来自持久化，而不是解析或引用翻译。
4. **余量在哪**（改造前结论，保留原文）：上限 `MAX_ROWS=20000` 是代码常量，时间余量几乎全部取决于持久化改造（真正的多行 `INSERT` 或 MyBatis `ExecutorType.BATCH`）；改造已于当日完成并复测，结果见 §6。内存侧即使 5 万行也远未触及 1GB（按 12MB/2 万行线性外推约 30MB，仅作参考，未实测）。
5. **同步导入的连接占用**：单次 2 万行事务约 7–8 秒（含提交），当前 Hikari 默认池下，同时 10 个导入就会打满连接池——这是“上限”之外更现实的风险。
6. **数据库侧**：压测期间 `Slow_queries=0`、`Innodb_row_lock_waits=0`、`Max_used_connections=5`、`Threads_connected=3`，无连接池告警、无死锁日志。

## 6. 批量写入改造与复测（2026-11-10 18:50–19:05）

### 6.1 改造方式与选型

- 改造点：`DemoTaskRepositoryImpl.insertBatch` 与 `PostRepositoryImpl.insertBatch` 原本都是 `for` 循环逐行 `mapper.insert`；改为 MyBatis `@Insert` + `<foreach>` 的多行 `INSERT ... VALUES (...),(...)`，每 1000 行一条语句，仍在外层 `@Transactional` 内分块执行。`@Transactional` 未改，任一条语句失败整批回滚，未分段提交。
- 选择手写多行 SQL、不用 `ExecutorType.BATCH` 的理由：
  1. **flush 时机**：BATCH 执行器在 Spring 事务里何时 `flushStatements()` 不由业务代码可见；Spring 负责提交，若未显式 flush，会话关闭时的 flush 可能晚于提交，出现语句未执行或事务边界错位，必须额外注入 `SqlSessionTemplate` 手动 flush。
  2. **是否真的合并**：BATCH 仍依赖驱动 `rewriteBatchedStatements` 才会合并网络包；手写多行 SQL 不依赖任何驱动参数，行为确定、可解释。
  3. **接入成本**：项目是 MyBatis-Plus，BATCH 需要按模块切换 `SqlSessionTemplate`，框架接入点要额外传参；多行 SQL 只需 Mapper 增加一个方法，两个接入点各一处。
  4. **回填差异**：BATCH 下 `useGeneratedKeys` 的回填行为随驱动版本不同；多行 SQL 若开启回填同样需要验证，因此两条路都不能默认“主键自动回填”。
- 已知代价：多行 SQL 绕过 MyBatis-Plus 的 `MetaObjectHandler`，`created_at` / `updated_at` 在 Repository 内显式填充（与单条插入同口径，UTC）；单条 `create` 路径完全未改。

### 6.2 主键回填

- 批量语句**未开启** `useGeneratedKeys`：导入路径不消费自增 ID（`ImportOutcome` 只回行数与导入数）。
- 因此批量插入后内存实体的 `id` 为 `null`。业务约束：**导入完成后不得依赖内存实体的 ID**，需要 ID 请重新查询。
- 若将来需要回填：在 Mapper 批量方法上加 `useGeneratedKeys=true`、`keyProperty="rows.id"`，MySQL 多行 `INSERT` 会返回全部自增键；需按驱动版本验证，本轮未启用，不承诺该行为。
- 单条插入（`mapper.insert`）仍由 MyBatis-Plus 回填 ID，行为不变。

### 6.3 批次大小对比（同机、同 `-Xmx1g`、每档先 3 行预热）

每档都是独立重建、冷 JVM，所以“首跑”包含 SQL 解析与 JIT；同 JVM 第二跑为热态。两跑都列出，避免只挑好看的数字。

| 批次 | 首跑：持久化 / 服务端合计 / 客户端 | 第二跑（热）：持久化 / 服务端合计 / 客户端 | 堆增长（首跑） | Full GC |
|---|---|---|---|---|
| 200 | 1,191 / 1,433 / 1,515 ms | 776 / 957 / 1,021 ms | +37.1 MB | 0 |
| 500 | 1,028 / 1,307 / 1,377 ms | 759 / 897 / 965 ms | +39.7 MB | 0 |
| **1000（采用）** | 1,038 / 1,267 / 1,334 ms | **621 / 757 / 816 ms** | +41.7 MB | 0 |

选择 1000 的依据：热态持久化比 200 低约 20%（621 vs 776 ms）、比 500 低约 18%；语句数从 100/40 条降到 20 条，单条 SQL 约 100–130 KB（按每行约 100–130 B 估算），远低于 MySQL `max_allowed_packet` 默认 64 MB；堆增长仅比 200 多 4.6 MB。批次间单跑波动约 10%–15%，但 200 与 1000 的差值超出波动范围，且有明确机制（往返次数）。

### 6.6 3 并发导入实测（不实现限流）

- 选择 3 × 20,000 行：20,000 是单请求上限、最坏量级；3 并发代表小团队同时导入，且未到池上限 10，可观察数据库/内存是否先饱和。
- 结果（热态，第二轮；三个请求同时发起）：

| 请求 | 客户端耗时 | 服务端合计 | 持久化 | 结果 |
|---|---|---|---|---|
| 并发 1 | 1,005 ms | 950 ms | 799 ms | 200 |
| 并发 2 | 1,012 ms | 956 ms | 828 ms | 200 |
| 并发 3 | 1,020 ms | 957 ms | 849 ms | 200 |

- 整体墙钟 1.48 s，无失败、无超时。
- Hikari：`peakActive=3`、`peakPending=0`（100 ms 轮询，21 次采样，经 `/actuator/metrics/hikaricp.connections.*` 带登录态读取）。

### 6.8 结论

- **2 万行从约 8 秒降到约 0.8–1.0 秒**（热态客户端）；新进程第一次导入 1.3–1.5 秒，差异来自 JIT 与首次 SQL 解析。持久化不再是瓶颈（占比从 96%–98% 降到约 80%–82%，剩余为解析、校验与整批实体构造）。
- 2 万行上限**保持不动**：持久化已不是限制项；当前限制项是并发连接占用与单请求内存。是否上调 `MAX_ROWS` 未实测，不在本轮结论内。
- 岗位（`sys_post`）接入点同步改为多行插入，3 行导入冒烟通过；未做 2 万行压测，不引用本报告的耗时数字。
