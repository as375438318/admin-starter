## 1. 背景

等保拆解里判定为**不符合**的一项：无口令复杂度校验、无过期策略、管理员初始口令 `admin123` 是弱口令且只靠启动日志提醒改密。这是测评必查项，也是唯一"应用侧能立刻闭环"的 P0。

## 2. 实现

### 2.1 数据（`V17__password_policy.sql`）

| 列 | 说明 |
|---|---|
| `password_updated_at` | 口令最近修改时间；**NULL 按已过期处理**（历史数据不能假设刚改过） |
| `must_change_password` | 1 = 下次登录必须改密 |

存量行一律置 `must_change_password = 1`——它们的口令全都产生于无策略时代。

### 2.2 校验（`PasswordPolicy`）

判定顺序（**弱口令优先于长度**：`admin123` 说"属于常见弱口令"比说"长度不足"更贴近事实）：

1. 空 → 拒
2. 弱口令表（30 项，含 `admin123`、`admin@123`、`12345678` 等），不区分大小写
3. 长度 ≥ 10 且 ≤ 64
4. 字符类 ≥ 3（大写/小写/数字/特殊）
5. 不得包含账号名（账号名 ≥ 3 位时才判定，避免 `ab` 这类误伤）
6. 不得含 3 个连续相同字符、不得含 4 位连续顺序字符

失败统一 `422 + 30202`，**message 指出具体原因**——只回"密码太简单"会让用户反复试错。

### 2.3 置位/清位

| 场景 | `must_change_password` |
|---|---|
| 创建用户 | 0（口令由创建者按策略输入） |
| 管理员重置 | **1**（新口令只有管理员知道） |
| 用户自助改密 | 0，并刷新 `password_updated_at` |
| 口令过期 | 登录响应 `passwordExpired = true`，效果等同必须改密 |

### 2.4 契约（新增字段，向后兼容）

`POST /api/v1/auth/login` 与 `/auth/refresh` 的响应新增 `mustChangePassword`、`passwordExpired`（boolean）。`docs/api/openapi.yaml` 版本 1.0.3 → **1.0.4**。

## 3. 测试

`PasswordPolicyTest` 14 条，重点不是"能拒绝"，而是**拒绝原因指向真正缺的那一项**：

| 覆盖 | 说明 |
|---|---|
| 合法口令通过 | 含特殊字符/不含账号名 |
| 空、过短、过长 | 长度上下界都明确 |
| 字符类不足 | 只有小写+数字被拒 |
| 弱口令 | `admin123` 与 `Admin@123`（大小写不敏感）都被拒 |
| 含账号名 | `Zhangsan#2026` 被拒；账号名 < 3 位不参与判定 |
| 连续字符 | 3 连相同、4 位顺序被拒；配置置 false 后放行 |
| 过期判定 | `null` 视为过期；到期日边界 |

**过程中修掉的自身错误**（记下来防复发）：
- 测试数据 `Aaa#456789x` 里只有 2 个连续 `a`（`A` 与 `a` 大小写不同），断言必错——说明我写用例时"看起来像 3 个"就当成 3 个；
- 迁移文件先写成 `V10__`，与既有 `V10__notification_module.sql` 撞号，Flyway 报 `Found more than one migration with version 10`；且增量构建的 `target/classes` 里残留旧文件名，改名后仍报同一错——**必须清掉编译产物残留**。
