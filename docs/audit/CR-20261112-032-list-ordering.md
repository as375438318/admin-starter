## 2. 问题：同一批列表两种默认顺序

`SortSupport.isAsc(order)` 对 `null` 返回 `true`，于是**"忘记传方向"等价于"升序"**。实测各列表默认顺序：

| 默认顺序 | 列表 | 用户直觉 |
|---|---|---|
| **升序（最早在前）** | 用户、参数、字典类型、定时任务、通知、操作日志、示例任务 | ❌ 反直觉，尤其是**操作日志**——排障时最想看最新的 |
| **降序（最新在前）** | 文件、回收站、会话、导出任务、任务执行日志、通知收件箱、通知已读人 | ✅ |
| **按 sort 升序** | 角色、岗位、部门、菜单、字典项 | ✅ 参考数据按人工排序号 |

即"默认值靠副作用产生"，同类列表出现两派。

## 3. 统一规则（本项目约定，已写入断言 #97）

| 规则 | 内容 |
|---|---|
| **L1 流水/事务类**（按 `created_at` 排序） | 默认 **DESC**：用户、参数、字典类型、定时任务、通知、操作日志、示例任务 |
| **L2 带人工排序号的参考数据**（按 `sort` 列排序） | 默认 **ASC**：角色、岗位、部门、菜单、字典项 |
| **L3 客户端可覆盖** | `?sort=<白名单字段>&order=asc|desc`；字段不在白名单**静默回落**默认列；方向非法值回落默认方向（不 500） |
| **L4 必须有次级键** | 主排序列相同（种子数据常见：同一语句插入，`created_at` 完全一致）时用 **同方向的 `id`** 兜底，否则翻页会重复/漏条 |

## 4. 代码改动

1. `SortSupport`：
   - `isAsc(order)` → `isAsc(order, defaultDescending)`，**默认方向强制由调用方声明**（不再有"不传就升序"的副作用）；
   - 新增具名常量 `NEWEST_FIRST` / `BY_SORT_COLUMN`，调用处读起来就是业务语义；
   - 新增 `applyOrder(wrapper, column, ascending)`：主列 + 同方向 `id` 次级键，避免每个仓储手写两行。
2. 9 个仓储改为 `SortSupport.applyOrder(wrapper, column, SortSupport.isAsc(query.getOrder(), <常量>))`：
   参数 / 示例任务 / 字典 / 定时任务 / 通知 / 操作日志 / 用户 → `NEWEST_FIRST`；岗位 / 角色 → `BY_SORT_COLUMN`。
3. 前端无需改动（通知页在 `CR-20261112-028` 里已显式传 `order=desc`，现在与默认一致，属冗余但保留以表达意图）。

## 5. 顺带修掉的真实缺陷：无次级键导致翻页不稳定

改第一版时 `order=asc` 的用例失败：**种子用户 `created_at` 完全相同**，没有次级键时 MySQL 按主键顺序返回，于是"时间正序但 id 倒序"的诡异组合出现了。这不是测试问题，而是**分页可能重复/漏条**的真实缺陷——已按 L4 统一用同方向 `id` 兜底。
