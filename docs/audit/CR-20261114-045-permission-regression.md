## 1. 背景

权限码有 71 个、内置角色 7 个，靠人眼核对矩阵与代码必然会漂移。典型漏配：新增接口加了 `@PreAuthorize`，但迁移里忘了给任何角色授权——上线后是全角色 403，且只有点进去才发现。

目标：把「权限码 × 角色」的允许/拒绝矩阵变成**可执行的回归用例**，并在 CI 里阻断漂移。

## 2. 做法

| 部件 | 作用 |
|---|---|
| `tools/permission-matrix/cli.mjs` | 扫 Controller 的 `@PreAuthorize` + `@RequestMapping`/`@*Mapping` 抽「权限码 → 代表性接口」；解析 `docs/design/permission-matrix.md` 的角色列；生成用例 JSON；`--check` 校验一致性（CI 用） |
| `server/web/src/test/resources/permission-matrix.json` | 生成产物（71 条用例 + 4 条字段级跳过 + 角色账号映射），**禁止手改** |
| `PermissionMatrixTest` 用例 1 | **授权数据层**：查库比对每个角色实际拥有的权限码集合与矩阵逐格一致（71 × 7 = 497 组合，精确、无副作用） |
| `PermissionMatrixTest` 用例 2 | **执行层**：真实 HTTP 调用，`GET` 与无请求体的 `DELETE` 要求拒绝方**正好 403**（证明 `@PreAuthorize` 真接在该权限码上） |

## 4. 关键取舍与盲区（不掩饰）

1. **带 `@Valid` 请求体的写接口只做弱断言**：Spring MVC 在调用 handler 之前完成参数绑定与校验，所以"无权限角色 + 空请求体"得到的是 422 而不是 403，请求根本没走到鉴权。为这类接口伪造合法请求体，会让业务校验一改就误红，而且大量写接口会产生真实副作用（见下面第 2 条）。因此这类组合登记为弱断言（不作为失败），其**授权是否正确由授权数据层用例覆盖**。
2. **写操作的"允许侧"必须用不存在的目标**：第一版把路径占位 `{id}` 替换成 `1`，导致 `DELETE /api/v1/roles/1` 真的把 `SUPER_ADMIN` 角色软删、`DELETE /api/v1/users/1` 把 `admin` 软删，测试库被我自己改坏。现在统一替换为哨兵值 `999999`：允许侧只会撞到"目标不存在"，不产生任何数据变更（已验证：跑完测试种子数据完好）。
3. **`hasAnyAuthority` 接口（如 `GET /api/v1/menus`）不做拒绝断言**：它本来就"有任一权限码即可"，单码维度不存在"应拒绝"。
4. **缺必填参数的接口**（如 `DELETE /api/v1/cache/keys` 需要 key）同样停在鉴权之前（400/10001），归入弱断言。
5. 字段级脱敏权限（`system:user:phone:view` 等 4 个）不是接口级权限，由 `MaskResolverTest`/`MaskedValueGuardTest` 覆盖，生成器把它们列为 `skipped`。

## 5. 顺带查出的环境事故（我的问题，已修）

排查过程中发现本地测试库 `admin` 用户与 `SUPER_ADMIN` 角色被**软删**（`deleted=1`），导致所有 SUPER_ADMIN 断言 403。时间戳显示是今天 12:23 我用 PowerShell 手工冒烟时误删的，不是测试套件行为。已用幂等 SQL 恢复（恢复角色、补全 79 条菜单授权、重建 `admin → SUPER_ADMIN` 绑定），并确认开发库未受影响。

> 教训：手工冒烟不要对生产形状的数据跑 `DELETE`。这条已写进断言 #114。
