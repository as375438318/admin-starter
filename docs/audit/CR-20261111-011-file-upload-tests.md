## 1. 背景

`FileAppService` 的上传链路（直传 / 秒传探测 / 分片）此前零测试，而它同时具备三类风险：

1. **校验形同虚设**：类型白名单、大小上限、分片大小与序号范围任一漏判，就能塞进任意文件或把存储打满；
2. **去重逻辑写错**：按 sha256 去重时若"复用路径"和"重新落盘"判断错，会产生打不开的文件（记录指向不存在的字节）或重复占空间；
3. **越权续传**：分片会话若不校验上传者，任何人都能往别人的会话里塞分片。

## 2. 范围（+15 用例，`FileUploadTest`）

**用真实 `LocalFileStorage`（指向 JUnit `@TempDir`）而不是 mock** —— "字节到底有没有落盘"正是这块最容易错的地方，mock 掉存储等于测出假绿。

| 分组 | 用例 | 锁定 |
|---|---|---|
| 直传校验 | 3 | 空文件拒绝；超过上限抛 `PayloadTooLargeException` 并带上限；扩展名不在白名单时提示带扩展名 |
| 直传正常路径 | 1 | 字节真的落盘、记录带 sha256/上传人/部门、响应 `instant=false` |
| **去重** | 2 | 相同内容且字节在库 → 复用存储路径、**仍建新记录**、标记秒传；**记录在但字节已丢 → 不秒传，重新落盘**（避免返回打不开的文件） |
| 秒传探测 | 2 | 参数校验（文件名/sha256 格式/大小）；命中返回文件、未命中 `instant=false` 且不带文件 |
| 分片会话 | 3 | 分片大小必须 256KB–5MB；正常开会话 `totalChunks` 上取整且状态 `UPLOADING`；命中秒传时不建会话 |
| 分片越权与边界 | 2 | 续传他人会话 403、会话不存在 404；序号越界/超过约定大小被拒且不写盘、不更新进度 |
| 分片累计 | 1 | 已上传序号去重排序后落库（`0` + 上传 `2` → `0,2`），分片字节落盘 |
| 匿名上传 | 1 | 无登录上下文时仍可上传（系统调用），但记录的上传人与创建人为空 |

## 8. 自我纠正（测试代码内，非产品缺陷）

1. 首版用了一个不存在的 `Sha256Utils` → 改为在测试内用 `MessageDigest` 独立计算（也避免"用被测代码验证被测代码"）；
2. "分片过大"用例起初用了 20MB 文件，结果**先撞到文件总大小上限**（`PayloadTooLargeException`）而不是分片大小错误 → 改为 6MB 文件 + 6MB 分片，让被测判断真正生效。这条写进注释，避免后来者重踩。
