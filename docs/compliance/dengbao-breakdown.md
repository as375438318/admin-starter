# 等保 2.0 条款拆解（自评估清单）

> 状态：**自评估清单，不是合规结论**。
> 依据：`AGENTS.md` §9-A「合规要求」一行要求「需过等保二级／三级；具体条款待拆解为可验收条目，未拆解前不得以"已合规"表述交付」。本文件即该拆解的落地件。

## 0. 三条前置事实（决定本文件能说什么、不能说什么）

| 事实 | 现状 | 影响 |
|---|---|---|
| **定级备案** | 未定级、未备案（等级由业务主管单位/行业主管部门确认，非技术方单方决定） | 无法确定适用二级还是三级；本文件按**三级为基线**列清单，二级取其子集 |
| **测评** | 未委托测评机构，无测评报告 | 任何"已合规"表述均无依据 |
| **条款编号** | 本文件**不引用 GB/T 22239-2019 的具体条款号** | 条款编号须对照标准原文逐条补齐；凭记忆写编号极易出错，宁可不写 |

> 因此本文件的用途是：**把"要通过等保"这个模糊目标，拆成可以逐条指派、逐条验证的工程任务**，并标出当前差距。

## 1. 方法

- 按 GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》的**控制点分类**组织：安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心、安全管理制度、安全管理机构、安全管理人员、安全建设管理、安全运维管理。
- 本项目是**单机内网部署的后台管理应用**，因此：
  - 物理环境、通信网络、区域边界的多数控制点由**机房/网络设备/运维**承担，应用侧只做"配合项"；
  - 应用侧能自主闭环的集中在**安全计算环境**（身份鉴别、访问控制、安全审计、入侵防范、数据完整性/保密性、数据备份恢复、剩余信息保护、个人信息保护）。
- 判定口径：**符合**（有实现 + 有证据）/ **部分符合**（有实现无证据，或实现不完整）/ **不符合** / **不适用**（附理由）。

## 2. 安全计算环境（应用侧主战场）

| 控制点 | 要求摘要（三级口径） | 本项目现状（证据位置） | 判定 | 差距与待办（优先级） |
|---|---|---|---|---|
| 身份鉴别·唯一性 | 每个用户唯一标识，禁止共用账号 | `sys_user.username` 唯一约束；`sys_user_role` 多对多；`sys_user_session` 记录设备与会话 | 符合 | — |
| 身份鉴别·复杂度与定期更换 | 口令复杂度、定期更换、首次登录强制修改 | **无密码复杂度校验**；无过期策略；仅启动日志提示「首次登录请改密」（`AdminApplication`） | **不符合** | **P0**：加密码策略（长度/字符类校验）、`password_updated_at` + 过期提醒、首登强制改密开关 |
| 身份鉴别·登录失败处理 | 限制连续失败次数、结束会话、超时退出 | `app.auth.max-login-failures=5`、`lock-duration=15m`（`AuthAppService` 原子计数）；`access-ttl=15m`、`refresh-ttl=7d` | 符合 | 建议补：失败锁定期间的**审计告警**（见安全审计行） |
| 身份鉴别·双因子 | 采用两种或两种以上组合的鉴别技术（三级要求） | 仅"口令"单一因子 | **不符合** | **P1**：短信/OTP/TOTP 至少一种第二因子，管理员账号强制；二级可评估为风险接受 |
| 访问控制·最小权限 | 分角色分权限，默认拒绝 | 权限码 + 角色 + 菜单/按钮级 `v-permission`；后端 `@PreAuthorize`；数据权限 fail-closed（未登记表直接报错） | 符合 | — |
| 访问控制·职责分离 | 关键操作需分离授权（如审计员不参与业务） | 内置 `auditor` 角色（只读审计）与业务角色分离 | 部分符合 | P2：明确"谁可改配置/谁可看审计"的岗位矩阵，写进 `docs/design/permission-matrix.md` |
| 安全审计·覆盖面 | 覆盖登录、退出、关键操作、权限变更 | `sys_login_log`（登录）+ `sys_oper_log`（受数据权限控制的操作日志，含 traceId/耗时/入参摘要） | 部分符合 | **P1**：确认"角色/权限变更""配置修改"都有审计；补审计查看入口的权限收紧 |
| 安全审计·留存与防篡改 | 日志留存不少于 6 个月，防未预期删除/修改/覆盖 | **留存策略未定义**（表内无归档/清理规则）；应用账号可删日志表数据 | **不符合** | **P0**：定留存期（≥6 个月）+ 归档策略；禁止应用账号 DELETE 审计表；导出到独立存储 |
| 入侵防范·最小功能 | 只开放必要端口与服务、关闭多余组件 | 生产只暴露 8080；Actuator 仅暴露 `health,info`；无 swagger 生产开关说明 | 部分符合 | P1：`springdoc` 生产环境关闭（或加鉴权），写进部署说明 |
| 入侵防范·恶意代码 | 上传文件检测 | 仅**扩展名白名单** + 大小上限；无病毒/内容检测 | **不符合** | **P1**：接入 ClamAV 或网关侧扫描；至少对 `zip/doc/xls` 做扫描 |
| 数据完整性 | 传输与存储完整性校验 | 传输：JWT + HttpOnly Cookie；上传按 **SHA-256 去重并校验整体一致性**（分片合并后比对 sha256） | 部分符合 | P1：生产强制 HTTPS（见下）；备份文件校验和 |
| 数据保密性·传输 | 重要数据传输加密 | `app.auth.cookie-secure` 可开（默认 false 因本地 HTTP）；无强制 TLS | **不符合**（生产未强制） | **P0**：生产强制 `APP_AUTH_COOKIE_SECURE=true` + 反代 TLS；启动时检测到 HTTP 且 cookie-secure=false 直接拒绝启动 |
| 数据保密性·存储 | 敏感数据存储保密 | 口令 **BCrypt** 哈希；手机号/邮箱**字段级三态脱敏**（明文/掩码/隐藏，fail-closed）；导出时无权限字段**整列不输出** | 部分符合 | P1：数据库层加密（列级或 TDE）待评估；备份加密 |
| 数据备份恢复 | 本地备份 + 异地/离线备份，定期恢复演练 | **无备份方案与演练记录** | **不符合** | **P0**：明确备份范围（MySQL + `data/uploads`）、频率、保留、恢复演练与责任人 |
| 剩余信息保护 | 鉴别信息与敏感数据释放前清除 | 软删除 + 彻底删除会按 `storage_path` 计数决定是否删物理字节（去重共享安全）；分片临时文件合并后清理 | 部分符合 | P1：定义"彻底删除"的数据擦除要求（介质层面由运维承担） |
| 个人信息保护 | 最小必要、访问授权、可追溯 | 字段脱敏 + 数据权限 + 操作日志 | 部分符合 | P2：补个人信息清单（哪些字段属个人信息、谁能看、留存多久） |
| 可信验证 | 基于可信根对关键组件做可信验证 | 未做 | 不适用（应用层） | 由基础设施/终端安全产品承担；测评时说明边界 |

## 3. 安全管理中心与其它技术类（多为运维/基础设施责任）

| 控制点 | 要求摘要 | 现状 | 判定 | 待办 |
|---|---|---|---|---|
| 集中管控/日志集中 | 日志集中收集、集中审计 | 应用日志输出到文件/控制台，未接集中平台 | 不符合 | P2：接 ELK/Loki 或运维统一采集 |
| 安全通信网络·网络架构 | 划分安全区域、带宽保障 | 单机内网，未划分区域 | 由运维承担 | 提供部署拓扑需求单给运维 |
| 安全区域边界·访问控制 | 边界防火墙策略、最小开放 | 未定义 | 由运维承担 | 明确入站仅 443（反代后）|
| 安全物理环境 | 机房物理访问控制、防火防水等 | 未定义 | 由运维/机房承担 | 索取机房等保测评结论作为佐证 |

## 4. 管理类（制度类）

| 分类 | 需要的产出 | 现状 |
|---|---|---|
| 安全管理制度 | 安全策略、管理制度、操作规程、记录表单四级文件 | 无 |
| 安全管理机构 | 岗位设置、授权审批、沟通合作机制 | 无 |
| 安全管理人员 | 人员录用/离岗/考核/安全意识培训 | 无 |
| 安全建设管理 | 定级备案、方案评审、产品采购、上线前测评 | 未开始 |
| 安全运维管理 | 日常运维、漏洞与补丁、配置管理、应急预案与演练 | 仅 CI/发布流程，无运维制度 |

> 管理类是**组织责任**，不是代码能解决的。技术上能做的只有：把制度要求的"可验证证据"（审批记录、变更记录、演练记录）落在仓库或工单系统里。

## 5. 差距优先级（可验收条目）

### P0（不补齐则无法通过测评，且都属"应用侧可自主完成"）

1. **密码策略**：复杂度校验 + 定期更换/过期提醒 + 首登强制改密
   - 验收：用 `admin123` 这类弱口令设置密码被拒；密码使用超过 N 天后登录被要求修改；新账号首登必须改密
2. **审计留存 ≥6 个月 + 防篡改**
   - 验收：给出留存与归档方案；应用账号无 `DELETE` 审计表权限；抽查 6 个月前日志可查
3. **生产强制 TLS**
   - 验收：`APP_AUTH_COOKIE_SECURE=true` 且反代 TLS 生效；以 http 直连时启动失败或明确告警
4. **数据备份与恢复演练**
   - 验收：备份任务清单（MySQL + uploads）+ 最近一次恢复演练记录

### P1

5. 双因子认证（至少管理员）——三级硬性要求
6. 上传文件恶意代码检测
7. 生产关闭 swagger/`springdoc`
8. 审计覆盖面补全（权限/配置变更）+ 失败登录告警
9. 数据库与备份的存储加密评估

### P2

10. 日志集中采集；岗位权限矩阵；个人信息清单；介质擦除要求

## 6. 需要业主方确认的事项（阻塞项）

| 事项 | 需谁答复 | 为什么阻塞 |
|---|---|---|
| 定级为**二级还是三级** | 业主/业务主管单位 | 决定双因子、集中管控、可信验证是否硬性 |
| 部署形态（单机 / 内网多机 / 云） | 业主 | 决定边界与物理项的责任划分 |
| 是否已有等保测评机构与整改预算 | 业主 | 决定时间表与整改范围 |
| 运维责任方（谁做备份、日志、补丁） | 业主 | 管理与运维项无法由开发方代替 |

## 7. 与其他文档的关系

- `AGENTS.md` §9-A 的合规行：本文件是对它的拆解，**不改变"未拆解前不得声明合规"的约束**——因为定级未定、测评未做，本文件只把"要做什么"列清。
- `docs/design/config-registry.yaml`：P0 中的密码策略、TLS 强制等会引入新配置项，落地时须登记台账（`SL-CFG-001`）。
- `docs/baseline/assertions.md`：已登记"安全相关既成事实"（脱敏三态、数据权限 fail-closed）；本文件的差距项落地后需追加断言。
