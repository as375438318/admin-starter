# ADR-007 前端框架主版本升级（Vite 8 / Vitest 5 / Vue Router 5 / Pinia 4）

| 项 | 内容 |
|---|---|
| 状态 | 已接受（2026-11-12，用户「没问题的 PR 就合并」批准；见 `CR-20261112-023`） |
| 决策日期 | 2026-11-12 |
| 影响范围 | `apps/pc` 构建与测试工具链、路由与状态管理库版本 |
| 关联 | `ADR-005`（技术栈基线）、`ADR-006`（前端测试框架）、`EVAL-20261112-001` |

## 背景

项目启动时（`ADR-005`）技术栈锁在 Vite 5 / Vitest 3 / Vue Router 4 / Pinia 2 那一代。Dependabot 上线后报出前端 5 个主版本跳跃，其中多个的 CI 检查是**全绿**——但"单测通过"不等于"升级安全"（测试覆盖不到主版本破坏面）。

同时存在另一面风险：**长期不升主版本**会让差距越拉越大，最终升级成本从"几天"变成"几周"，且拿不到上游的安全修复与新特性。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 不升，长期锁定 | 零风险、零工作量 | 差距持续扩大；安全修复进不来；未来一次性跳跃风险更高 | 否决 |
| B. 只升打包器（Vite 8 + plugin-vue 6） | 风险最小 | 有意义的收益也最小；Vitest/Router/Pinia 仍停在老线 | 否决 |
| C. **成套升级（采用）** | 一次解决版本线，工具链互相兼容；分包与构建更快 | 需要一次完整回归（构建 + 单测 + E2E + 人工点页） | **采用** |
| D. 分两年逐步升 | 单次风险小 | 中间状态（如 Vite 8 + Vitest 3）是未验证组合，长期维护成本高 | 否决 |

## 决策

采用方案 C，`apps/pc` 升级到：

| 依赖 | 前 | 后 |
|---|---|---|
| `vite` | 5.4.11 | **8.3.7** |
| `@vitejs/plugin-vue` | 5.2.0 | **6.0.10** |
| `vitest` | 3.2.7 | **5.1.0** |
| `@vitest/coverage-v8` | 3.2.7 | **5.1.0** |
| `vue-router` | 4.4.5 | **5.5.0** |
| `pinia` | 2.2.6 | **4.1.0** |

`vue` / `element-plus` / `typescript` / `axios` 保持现有版本（同主版本，另行 minor 批处理）；`element-plus` 的 minor 跟进建议与下批一起做。

## 依据（实测，不是推演）

见 `EVAL-20261112-001`：

- 构建通过（删除 `dist` 与 tsbuildinfo 后干净重建）；
- 单测 **95/95** 通过；
- **起后端跑 Playwright E2E：7/7 通过**（含后端菜单下发的动态路由注册、Pinia 鉴权 store、通知/文件/导出三条业务流）；
- 源码改动 **0 行**，只动 `package.json` 与 `pnpm-lock.yaml`。

## 后果

- `AGENTS.md` 技术栈表（前端框架行、测试框架行）同步更新到新版本线；
- 新增发现：`403.vue`/`404.vue` 在路由中被静态与动态同时引入（`INEFFECTIVE_DYNAMIC_IMPORT`），本决策同批修复；
- `dependabot.yml` 的"主版本忽略"策略**保持不变**——主版本仍应人工发起并走 ADR；
- 回滚：单提交 `git revert` 即恢复旧版本线（锁文件一并回滚）。

## 未覆盖

- E2E 仅 7 条，合并后建议人工点一遍重点页（列表、表单、导入导出、权限按钮）；
- `vitest.config` 的覆盖率阈值在 Vitest 5 下需复核（本次未跑 coverage 全量）。
